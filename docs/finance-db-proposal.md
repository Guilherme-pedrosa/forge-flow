# Contratos financeiros — revisão de 12/09/2026

O frontend usa exclusivamente estas operações transacionais; não há fallback com gravações independentes. Root administra a migration e aplicação direta, sem mensagens ao agente Lovable.

- `register_bank_transaction(p_bank_account_id uuid,p_type text,p_amount numeric,p_date date,p_description text,p_request_id uuid)`: tenant/usuário autenticado, conta ativa mesmo tenant, tipo credit/debit, valor positivo em centavos, data não futura. Inserir transação e ajustar saldo atomicamente. Request id único por tenant; retry com mesmos parâmetros retorna transação existente e nunca ajusta novamente. Reutilização de id com payload diferente deve falhar.
- `settle_financial_title(p_kind text,p_title_id uuid,p_amount numeric,p_date date,p_bank_account_id uuid,p_request_id uuid)`: kind payable/receivable; lock título e conta, verificar mesmo tenant e título não cancelado/estornado; valor > 0 <= saldo. Registrar bank_transaction debit/credit com reference_type accounts_payable/accounts_receivable e reference_id título, somar valor pago/recebido, manter partial até saldo zero. Data representa a última baixa, e histórico completo fica nas transações. Não apagar histórico. Invalidar payables/receivables, bank_accounts, bank_transactions, dre e dashboard no frontend.
- `create_purchase_order(p_order jsonb,p_items jsonb,p_installments jsonb,p_request_id uuid) -> uuid`: objetos são whitelist dos campos existentes, sem tenant_id/created_by/id/status confiados do cliente. `p_order.code` é omitido para geração no servidor; todas as criações começam pending. Campos p_order: vendor_id, order_date, expected_date, subtotal,discount,shipping,total,nfe_number,nfe_key,nfe_xml,notes. Item: description,quantity,unit_price,total,cfop,ncm,inventory_item_id,notes. Installment: description,amount,due_date,competence_date,vendor_id,payment_method_id,installment_number,installment_total,notes. Validar data, descrições, quantidades positivas, preços finitos não negativos, total e soma das parcelas em centavos, e vínculos mesmo tenant. AP recebe origin_type purchase_order + origin_id do PO. Competência das parcelas é data da compra (não vencimento); conta contábil inicialmente sem classificação. NFe deve ser única por tenant+nfe_key quando presente. Importação de screenshot nunca deve marcar como pago baseada em inferência de IA.
- `receive_purchase_order(p_order_id uuid,p_received_date date)`: bloquear PO e itens; impedir cancelado; received retorna sem repetir estoque (idempotência). Exigir itens existentes e vínculos válidos. Uma transação para todos os movimentos e status final. `quantity` dos itens vinculados precisa estar na unidade do estoque; frontend acrescenta campo explícito de conversão. Sugestão adicionar `purchase_order_items.stock_quantity numeric`, nullable para exigir conversão quando unidade de compra não é conhecida. Valor de estoque rateado é total do pedido proporcional ao total da linha; unit_cost = custo rateado / stock_quantity. Cuidado com compras de filamento: 1 rolo não é 1 grama.

Correções de registros antigos não devem reinterpretar `current_balance` automaticamente sem comparação com transações e saldo inicial. Registrar diagnóstico antes de migrar dados.
